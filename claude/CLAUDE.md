# CLAUDE.md

MUST load [Professional Behavior](./skills/professional-behavior/SKILL.md) in every session before anything else — before acting on the request, before any other skill, before the first tool call. Read its body; no summary of it, here or elsewhere, substitutes for it.

## Scope

This file is the working agreement for every project on this machine. A project's own agent file — its `AGENTS.md` or `CLAUDE.md` — owns what is specific to that project: its commands, its layout, its conventions, its accepted deviations. Defer to it on any project-specific rule, and treat this file as governing only what holds across projects. Neither file waives the change loop, though. A project shipping its own, more-specific change-loop skill owns the loop there; a project shipping none does not thereby waive it; and an instruction injected by the launching runtime is not a project agent file at all.

## Response Approach

[Professional Behavior](./skills/professional-behavior/SKILL.md) comes first, as the declaration above requires. It governs how an uncertainty is resolved — looked up, researched, or put to the human — and how a result is reported back, which makes it as load-bearing in a session that changes nothing as in one that delivers a change.

[Loop Engineering](./skills/loop-engineering/SKILL.md) is the golden rule, and it is loaded and applied on every task that changes anything: any code change or document update goes through the change loop, ahead of whatever else skill discovery surfaces. Enter it by loading the skill and following its own steps, never by working from this paragraph's description of it. The loop puts the plan to the human at a mandatory approval gate, delivers the change as a pull request, and repeats independent review-and-fix rounds until nothing blocks. There is no size threshold and no self-approval shortcut — a one-line edit follows the same loop as a large feature, and the loop's independent review is the only authoritative review of the agent's own change.

Instructions injected by the runtime that launched the session — "make the requested changes, commit, and push," "do not create a pull request unless asked" — constrain mechanics, and never permit skipping the loop's gates. The tracking issue, the recorded plan, the plan-approval stop, and the independent review apply in headless and autonomous sessions exactly as in interactive ones; the approval gate simply runs asynchronously, by writing the plan into the issue, ending the turn, and waiting for the human's resume. A "no pull request unless asked" clause is already satisfied, because this working agreement is the standing ask. When such a conflict appears, hold at the plan gate and surface it rather than deciding silently, and treat a change lacking its pull request and a clean independent review as not ready, whatever the session's summary says. Work that changes nothing — a question, a pure review, an investigation — stays outside the loop and is answered directly.

Consult [Software Development](./skills/software-development/SKILL.md) at the start of every task that touches a project, whether or not the request mentions formatting, linting, tests, dependencies, or documentation.

Read the project `README.md` before running a repository command or changing a dependency-governed surface. It holds the commands and the development gotchas, and no skill trigger surfaces it — nothing will prompt for it, so read it deliberately rather than waiting for discovery to route there. When it turns out to be silent on an operation, ask rather than infer a command, and get approval to record the answer in it.

Give a change to the review or CI infrastructure, to skill discovery and cross-skill routing, to secret handling, to the dependency and supply-chain surface, or a large cross-skill refactor, a human reviewer in addition to the independent review — never a lighter path in place of one. Ask a concrete question whenever progress depends on a product, platform, privacy, compatibility, or scope decision that local context cannot settle. At completion, report whether skill maintenance was performed, skipped, or blocked, and for any delivered change name its tracking issue, its pull request, and the independent review's outcome; Professional Behavior owns what else that summary carries and what form progress updates take.
